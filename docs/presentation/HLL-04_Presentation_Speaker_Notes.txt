SLIDE 2: The data collection problem
Target: 50 seconds. Main talk target 770 seconds (12 minutes 50 seconds).

Consider a basic workflow where a person copies photos into a folder and types descriptions into a spreadsheet. Each row must continue to refer to the intended image. Missing fields, mistaken filenames and plausible but incorrect descriptions are different failure modes. These are illustrative risks; I have not measured their frequency in a company. The proposed interface brings image import, metadata entry, review and export together. That can make certain mistakes easier to prevent or recover from, but it also introduces a cost: more structure may take longer or feel restrictive. The project must evaluate both the data and the work needed to produce it.

SLIDE 4: Design foundations
Target: 60 seconds. Main talk target 770 seconds (12 minutes 50 seconds).

The design builds on established work. Hartung and colleagues describe Open Data Kit as a modular collection architecture. Structured collection and required fields are therefore prior art, not inventions of this project. Bargas-Avila and colleagues provide guidelines for clear labels, required fields and error handling. Their discussion supports retaining entries after errors, but it does not prove that this prototype's blur-time validation is optimal. The chapter recommends feedback after submission, while this interface combines blur feedback with a final save gate. The contribution is a scoped implementation, repair and evaluation of this particular workflow. It is not a claim of superiority to ODK.

SLIDE 6: Validation at the point of entry
Target: 65 seconds. Main talk target 770 seconds (12 minutes 50 seconds).

The original guided validation checks presence, format and allowed values. In study mode it also requires an assigned task ID and rejects duplicate IDs. The frozen v2 checks covered corrupt images, a failed replacement and an old asynchronous import. A value can be permitted by the schema and incorrect for a task. Accuracy therefore needs a separate check against the declared task labels.

SLIDE 7: Recovery from a storage failure
Target: 75 seconds. Main talk target 770 seconds (12 minutes 50 seconds).

The storage-recovery evidence on this slide belongs to frozen v2 on 21 October. The earlier design stored image data in localStorage and could not support the selected workload. The repair uses a transactional IndexedDB snapshot and acknowledges a save after transaction completion. In a deliberately induced abort, one record remained in durable storage while the page held two accepted records and a separate unfinished draft. The recovery ZIP retained that work separately. Retry and reload then restored it. A separate quota override did not produce a failure, so this does not prove natural quota recovery. In remote v3, the new walkthrough retained guided work and table images through refresh, but its task-reference panel reset. Preserving data and preserving the visible context are different requirements.

Point to the warning first. Explain that working memory and persistent storage differ.

SLIDE 8: Traceable export
Target: 60 seconds. Main talk target 770 seconds (12 minutes 50 seconds).

The ZIP contains images, a CSV and a raw JSON manifest. Image hashes connect the metadata to particular prepared bytes. The frozen v2 test independently checked archive members, image hashes and agreement between the CSV and manifest at two checkpoints. These checks establish the content and consistency of the downloaded files. They do not establish scene truth or participant usability.

SLIDE 11: Remote workflow comparison (v3)
Target: 80 seconds. Main talk target 770 seconds (12 minutes 50 seconds).

The remote human method is a new browser-table comparison. Each permitted adult volunteer uses both conditions in the same sitting on their own desktop Chrome. The server alternates starting order across assignments. Each condition starts with a separate two-minute practice and then six assigned tasks, with a fifteen-minute maximum. Both conditions show the same task cards and image choices, and require explicit image selection. The table uses raw text cells. The guided condition retains its validation and review. Block time includes checking, correction, export and self-reported file inspection, but excludes questionnaire and final-upload time. Normal completion requires a current export and file confirmations. People can also finish incomplete, reach the cap or skip. Missing tasks remain in the twenty-four-cell denominators. The exploratory target is six to eight permitted adults, subject to the required arrangements. No human observations are available for this report. Frozen v2 retains its different folder-and-spreadsheet protocol.

Additional panel answers
Remote v3 changes the baseline from a folder/spreadsheet to an in-browser table, allows different participants to use different computers, and uses self-reported local file checks. It therefore cannot be silently pooled with v2. The server submission status is separate from analysis eligibility. Quality, completed timing and valid SUS each need their own eligibility and paired sample size. The synthetic S004/S005 runs cannot enter participant results. Consent screens do not imply institutional approval.

SLIDE 13: Backup: Evaluation measures
Backup slide for questions, outside the main talk.

Completeness is the fraction of all assigned required cells that are nonempty. Accuracy uses the same denominator and checks the declared truth. Six tasks give twenty-four cells per condition. Missing tasks remain missing. Task identity and selected-image hash matches are assessed separately. For remote v3, block time includes export generation and self-reported file checks, then stops before final upload. That differs from researcher-verified file inspection in v2. SUS is a ten-item zero-to-one-hundred composite. An absent answer is not imputed, and valid SUS pairs can differ from valid timing or quality pairs. Both questionnaires in synthetic session S005 were skipped, so that run has no SUS score. Human outcome data are unavailable for this report.

SLIDE 17: Backup: Remote v3 on AWS
Backup slide for questions, outside the main talk.

This slide describes remote-table-v3, separate from the original static v2 deployment. Amplify serves the study pages and prepared fictional assets over HTTPS. Lambda handles invitation and private session authorization. DynamoDB tracks assignments and accepted receipts, while a private S3 bucket holds metadata snapshots. The browser retains image bytes and produces local ZIP exports. Submitted study payloads include agreed task metadata, selected-image hashes, progress, timing observations and questionnaire responses, but no image contents. The S005 readback confirmed this boundary for the tested final payload. The API has private authorization and bounded small-study safeguards, but this is not a security or scale audit. The public landing page needs a private invitation. The separate human and synthetic invitations and resume credentials must remain private.

Give the short explanation first. Use the additional defence answers only for the panel’s specific questions.

Additional panel answers
The backend documents a four-hour collection window and a ninety-day retention policy. TTL and S3 lifecycle processing are asynchronous, so they do not guarantee deletion at an exact time. Withdrawal can be pending and must not be described as completed until cleanup is acknowledged. The 26 October walkthrough did not test withdrawal. The original static v2 host and its earlier EC2 test runner are separate infrastructure. Do not describe the remote metadata collector as browser-only storage or as a store of uploaded photographs. No new EC2 application server is used.
